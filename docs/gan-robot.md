# GAN Robot 协议研究与当前实现

本文记录 GAN Robot 的 BLE GATT 结构、命令格式、执行时序、封包观察结果，以及当前项目的实现情况。

目前的真机验证和项目实现以 Robot V2 为主。Robot V1 的协议定义也已整理完成，虽然因缺少对应硬件而暂不实现，但仍完整保留在本文中作为协议研究资料。

## 1. Robot V1 协议

### 1.1 设备识别与协议选择

已知协议选择关系如下：

| 设备识别 | 读取协议 | 写入协议 | 备注 |
|---|---|---|---|
| 名称以 `gan-` 开头，设备类型为 `GANRO` | Robot V1 | Robot Write V1 | 旧版 Robot 路径 |
| 名称以 `ganbot-` 开头 | Robot V1、Robot V2 | Robot Write V2 | 设备可能同时兼容两套读取协议 |

这里的 V1/V2 指协议与 GATT 结构版本，不一定等同于产品宣传名称或 firmware 版本。设备可能同时登记多套读取协议，因此不能只根据名称推断最终使用的 characteristic。

### 1.2 GATT 结构

Robot V1 的主服务为：

| 项目 | UUID |
|---|---|
| Service | `8653000A-43E6-47B7-9CB0-5FC21D4AE340` |
| Notify characteristic | `8653000B-43E6-47B7-9CB0-5FC21D4AE340` |
| Read / write characteristic | `8653000C-43E6-47B7-9CB0-5FC21D4AE340` |
| CCCD | `00002902-0000-1000-8000-00805F9B34FB` |

V1 使用一组自定义 `8653...` UUID 承载通信，但协议字段仍登记为 `FFF0/FFF1~FFF5` 等逻辑位置。这表示“协议命令的逻辑位置”与“设备实际暴露的 GATT characteristic”之间存在一层映射，不能把短 UUID 直接当成 V1 真机上的完整 characteristic UUID。

### 1.3 读取协议字段

| appProtoId | BLE 逻辑位置 | 字段 | 格式 |
|---:|---|---|---|
| 2 | `FFF0 / FFF2` | `remainFormulas` | 1 byte，剩余公式数量 |
| 5 | `180A / 2A23` | `macAddress` | 6 bytes，以冒号连接 |
| 6 | `180A / 2A24` | `model` | 最多 16 bytes，ASCII |
| 7 | `180A / 2A25` | `serialNumber` | 7 bytes |
| 8 | `180A / 2A26` | `version` | 7 bytes |
| 9 | `180A / 2A27` | `deviceVersion` | 3 bytes，以 `.` 连接 |
| 10 | `180A / 2A28` | `version`、`date` | 版本 3 bytes，日期 3 bytes |
| 11 | `180A / 2A29` | `manufacturer` | 最多 16 bytes，ASCII |

### 1.4 写入协议命令

| appProtoId | 目标位置 | action | 用途 |
|---:|---|---:|---|
| 1 | `FFF0 / FFF1` | 0 | `order`，1 byte 控制命令 |
| 2 | `FFF0 / FFF2` | 1 | 读取剩余公式数量 |
| 3 | `FFF0 / FFF3` | 0 | 写入公式序列 |
| 4 | `FFF0 / FFF5` | 0 | 写入单步机械动作 |
| 5～11 | `180A / 2A23~2A29` | 1 | 读取设备信息 |
| 12 | `FFF0 / FFF4` | 0 | 写入 RGB 灯效 |

`action=0/1` 表示协议描述中的写入／读取动作类型；具体映射仍应以调用层语义为准。

### 1.5 V1 公式序列

V1 的 `FFF3` 公式字段同样定义为 4-bit 数组：

- 每个动作占 4 bit。
- 字段容量为 36 个 nibble，即 18 bytes。
- 动作编码为 `R/F/D/L/B` 五个面，每面分别提供顺时针、180 度和逆时针，共 `0x0~0xE`。
- `0xF` 不对应机械动作，可作为公式结束或空位标记。
- 没有原生物理 `U` 动作。

V2 真机已确认使用 `0xF` 结束公式并在其后补 `0x00`；V1 缺少硬件验证，因此不能直接断定它的尾部 padding 与 V2 完全一致。

### 1.6 V1 单步动作 `FFF5`

V1 的单步机械动作格式为：

```text
byte 0      = 0x21
byte 1      = direction
byte 2      = surface
byte 3..4   = turns，16-bit，大端
```

字段定义：

| 字段 | bitCount | 说明 |
|---|---:|---|
| `defaultData` | 8 | 固定值 `33`，即 `0x21` |
| `direction` | 8 | 方向编码，枚举未确认 |
| `surface` | 8 | 机械表面编码，枚举未确认 |
| `turns` | 16 | 转动量，大端序，单位未确认 |

### 1.7 V1 `FFF1` order

`FFF1` 写入一个名为 `order` 的 8-bit 字段。协议定义没有列出 command enum，因此目前只能确认它是控制命令入口，无法确定每个值的含义。

### 1.8 V1 `FFF4` RGB

写入格式为：

```text
byte 0 = op，固定为 0x03
byte 1 = r，协议定义中的默认值为 0
byte 2 = g
byte 3 = b
```

颜色范围、灯效持续时间，以及是否需要先写入 `FFF1`，均未经过 V1 真机确认。

### 1.9 V1 与 V2 的主要差异

- V1 使用 `8653000A/0B/0C` 自定义 GATT 结构；当前 V2 真机使用标准 `FFF0/FFF2/FFF3/FFF4` 路径。
- 两个版本的公式、单步动作、设备信息和 RGB 命令定义大致相同。
- V2 另外定义了带事件类型的状态通知，可表达 `cubeOn`、`robotReady`、`robotStatus` 和 `robotTime`。
- V1 RGB 定义中 `r` 带默认值 `0`；V2 的 `r/g/b` 都是普通输入字段。
- V1 目前只有协议定义，没有真机封包验证；V2 以下章节同时包含协议定义与实测结果。

## 2. Robot V2 GATT 结构

### 2.1 当前真机使用的特征值

| 用途 | UUID | 属性／方向 |
|---|---|---|
| Robot service | `0000FFF0-0000-1000-8000-00805F9B34FB` | Service |
| 控制命令 | `0000FFF1-0000-1000-8000-00805F9B34FB` | Write，具体命令值待确认 |
| 动作剩余量 | `0000FFF2-0000-1000-8000-00805F9B34FB` | Read |
| 公式动作 | `0000FFF3-0000-1000-8000-00805F9B34FB` | Write |
| 状态／按钮／RGB | `0000FFF4-0000-1000-8000-00805F9B34FB` | Notify，另有 Write 定义 |
| 单步机械动作 | `0000FFF5-0000-1000-8000-00805F9B34FB` | Write，格式已知但参数枚举待确认 |
| CCCD | `00002902-0000-1000-8000-00805F9B34FB` | 开启 `FFF4` notification |

当前已验证的主要执行链只需要：

1. 向 `FFF3` 写入公式。
2. 从 `FFF2` 读取剩余动作数，判断本次公式是否完成。
3. 监听 `FFF4`，接收初始化状态和实体按钮事件。

在连接自检、方向探测、打乱和复原的封包中，没有观察到必须配合写入 `FFF1` 或 `FFF5` 的情况。

### 2.2 另一组 V2 read/write UUID

协议描述中还存在以下一组 V2 UUID：

| 用途 | UUID |
|---|---|
| Read characteristic | `5833FF01-9B8B-5191-6142-22A4536EF123` |
| Write characteristic | `5833FF02-9B8B-5191-6142-22A4536EF123` |

当前真机实际使用标准 `FFF2/FFF3` 路径，尚未确认什么固件或硬件会使用 `5833FF01/5833FF02`。实现时不应在未发现对应 GATT capability 的情况下主动切换到这组 UUID。

### 2.3 Device Information Service

协议还登记了标准 Bluetooth Device Information Service：

| UUID | 字段 | 格式 |
|---|---|---|
| `180A/2A23` | MAC address | 6 bytes，以冒号连接 |
| `180A/2A24` | Model | 最多 16 bytes，ASCII |
| `180A/2A25` | Serial number | 7 bytes |
| `180A/2A26` | Hardware revision | 7 bytes |
| `180A/2A27` | Firmware revision | 3 bytes，以 `.` 连接 |
| `180A/2A28` | Software revision/date | 版本与日期字段 |
| `180A/2A29` | Manufacturer | 最多 16 bytes，ASCII |

这些字段不是动作执行的必要条件，但以后可以用于区分 firmware、硬件批次和 GATT variant。

## 3. `FFF3` 公式协议

### 3.1 Payload 格式

`FFF3` 使用固定 18 bytes payload，每个动作占一个 4-bit nibble：

- 动作依次写入 high nibble、low nibble。
- `0xF` 不是动作，而是公式结束标记。
- 结束标记后的剩余 bytes 填 `0x00`。
- 18 bytes 共 36 个 nibble，其中必须保留一个给结束标记，所以单个 `FFF3` 最多携带 35 个动作。
- 超过 35 个动作时必须拆成多个 `FFF3` 作业，每个作业各自带 `0xF` 结束标记。

### 3.2 动作编码表

Robot 只有五个物理转轴，编码中没有原生 `U` 动作。

| 动作 | Nibble | 动作 | Nibble | 动作 | Nibble |
|---|---:|---|---:|---|---:|
| `R` | `0x0` | `R2` | `0x1` | `R'` | `0x2` |
| `F` | `0x3` | `F2` | `0x4` | `F'` | `0x5` |
| `D` | `0x6` | `D2` | `0x7` | `D'` | `0x8` |
| `L` | `0x9` | `L2` | `0xA` | `L'` | `0xB` |
| `B` | `0xC` | `B2` | `0xD` | `B'` | `0xE` |

### 3.3 编码示例

单个 `R`：

```text
nibbles: 0, F
payload: 0F 00 00 00 ...
```

方向探测 `D F`：

```text
nibbles: 6, 3, F
payload: 63 F0 00 00 ...
```

五轴连接自检 `R F D L B`：

```text
nibbles: 0, 3, 6, 9, C, F
payload: 03 69 CF 00 ...
```

### 3.4 `FFF3` 作业与语音提示

真机行为表明，语音提示更接近“开始一个普通 `FFF3` 作业”，而不是每个机械动作一次：

- 一条较短的复原公式若只占一个 `FFF3`，通常只播放一次“工作中”提示。
- 长公式被拆成多个 `FFF3` 后，可能每个分包都重新播放一次提示。
- 因此不应为了保守而主动缩短分包；只要不超过 35 个动作，应尽量一次写完。
- `D F` 方向探测作为一个固定公式发送时，实测不会在探测阶段播放“工作中”提示。
- 连接初始化阶段发送固定的 `R F D L B` 自检序列，实测也不会播放“工作中”提示。

目前还不能完全区分“不播放语音”是仅由固定公式决定，还是同时要求它出现在连接初始化或方向探测的特定时序中。当前实现同时保持相同的公式与时序，不额外依赖未知控制 byte。

## 4. `FFF2` 动作状态

### 4.1 已确认语义

读取 `FFF2` 后，当前只需要第一个 byte：

```text
movesRemaining = payload[0] & 0xFF
```

- `movesRemaining > 0`：当前 `FFF3` 仍有动作尚未完成。
- `movesRemaining == 0`：当前作业已经完成或设备处于 idle。

`FFF2` 是查询整条公式的剩余动作数，不需要每完成一个动作就读取一次。打乱和复原流程都是写入一个公式后周期性查询，直到回到 `0`。

### 4.2 查询时序

封包观察中常见约 400ms 的查询间隔，但这不是协议要求。查询过慢会把已经完成的动作延迟到下一次轮询才发现，直接增加 probe 和整条公式的等待时间。

当前实现采用以下策略：

- 普通公式写入后先等待 100ms。
- 剩余动作大于 2 时，每 200ms 查询一次。
- 剩余动作小于等于 2 时，每 100ms 查询一次。
- 方向探测已经由智能魔方状态变化确认动作开始，因此立即进行第一次查询，之后每 100ms 查询一次。

为了避免在 Robot 尚未更新状态时把第一个 `0` 误判为完成：

- 若已经观察到非零值，后续第一个 `0` 即可判定完成。
- 若普通公式从未观察到非零值，需要连续读取两个 `0` 才判定完成。

这套轮询只负责确认作业完成，不负责检查魔方是否真的转对。实际方块状态由智能魔方链路独立同步。

## 5. `FFF4` 通知

连接后需要为 `FFF4` 写入 CCCD，开启 notification。

### 5.1 已观察到的事件

连接初始化时出现过：

```text
03 00 00 FF 00 00
```

该数据符合以 `0x03` 作为事件类型，后续包含 `r/g/b/cubeOn/robotReady` 的结构，但各字段在当前 Robot 上的准确语义尚未完成验证。

实体按钮单击时出现：

```text
02 FF
```

当前实现将首 byte 为 `0x02` 的通知作为实体按钮事件，并根据用户设置触发复原、打乱或忽略。

协议描述中还存在 `0x04` 类型，字段包括：

```text
len
robotStatus
robotTime[4]
```

`robotStatus` 的枚举和 `robotTime` 的单位尚未确认，当前也没有用它替代 `FFF2` 完成轮询。

### 5.2 CCCD 与后续写入时序

Android BLE 的 descriptor write 与 characteristic write 不能重叠。如果在 `FFF4` CCCD 尚未写完时立即写 `FFF3`，可能出现：

```text
writeCharacteristic() - prior command is not finished
```

因此连接初始化必须遵循：

1. 发现 `FFF0` service。
2. attach `FFF2`、`FFF3` 和 `FFF4`。
3. 为 `FFF4` 写入 CCCD。
4. 等待 `onDescriptorWrite`。
5. 再发送连接自检或其它 `FFF3` 命令。

这里需要等待真实 GATT callback，不应依赖任意固定 sleep。

## 6. 连接自检协议行为

连接完成后，Robot 会依次转动五个物理轴：

```text
R F D L B
```

它不是五次独立写入，而是一条 `FFF3` 公式：

```text
03 69 CF 00 ...
```

正确时序是在 `FFF4` CCCD 写入完成后立即发送，再通过 `FFF2` 等待完成。真机测试中：

- `FFF2` 首次可读到剩余数 `5`，证明五个动作进入同一个作业。
- 五轴自检约一秒内完成，具体时间会受 BLE 查询点影响。
- 开机仍只播放 Robot 的问候语音，不会额外播放“工作中”提示。

自检完成后再进行 solver 预热，避免建表工作改变连接初始化命令的发送窗口。

## 7. 方向探测与公式发送

### 7.1 为什么需要方向探测

Robot 缺少的是物理 `U` 轴，但智能魔方的逻辑 `U` 面不一定朝向 Robot 的上方。实际映射会受到以下因素影响：

- App 当前训练模式的朝向定义。
- 魔方放入 Robot 时的方向。

因此不能固定禁止逻辑 `U` 面，必须先找出“哪个逻辑面映射到 Robot 的物理 U 轴”。

### 7.2 `D F` 单包探测

探测公式固定为：

```text
D F
```

当前流程只写入一次 `FFF3`：

```text
63 F0 00 ...
```

虽然 Robot 连续执行两个动作，应用仍可从智能魔方事件中依次取得：

1. 执行物理 `D` 后的状态。
2. 执行物理 `F` 后的状态。

比较前后状态即可识别物理 `D`、物理 `F` 分别对应哪个逻辑面，再推导完整的 `logical -> physical` 六面映射。这样既保留两次状态判断，又不会把 `D` 和 `F` 拆成两个 Robot 作业。

### 7.3 状态到状态的复原或打乱

状态到状态流程使用探测完成后的魔方状态直接求解：

1. 发送 `D F` 并取得探测后的状态。
2. 建立逻辑面到 Robot 物理轴的映射。
3. 找出映射到物理 `U` 轴的逻辑面，将它设为求解器禁用面。
4. 从探测后的状态求解到目标状态。
5. 将逻辑公式映射成物理公式。
6. 将物理公式写入 `FFF3`，并通过 `FFF2` 等待完成。

因为求解起点已经是探测后的状态，不需要先单独发送 `F' D'` 回滚探测动作。正常情况下，探测阶段不播放“工作中”，正式公式又可放入单个 `FFF3`，所以整次流程只出现一次工作语音。

手动输入固定公式时没有“从当前状态求解到目标状态”的步骤，因此会先在最终公式前加入 `F' D'`，把探测动作回滚后再执行用户公式。

## 8. 五轴限制与 `U` 动作

### 8.1 五面求解

对于状态到状态的打乱与复原，最有效的方式不是先生成普通六面解法，再把物理 `U` 展开成机械宏，而是直接寻找不使用该物理轴的五面解法。

“禁用面”必须根据方向探测动态选择。例如某次映射为：

```text
logical L -> physical U
```

此时求解器应禁用逻辑 `L`，而不是固定禁用逻辑 `U`。

五面求解带来的协议层收益是：

- 公式通常可控制在单个 `FFF3` 的 35 动作上限以内。
- 不会因 `U` 宏展开产生大量额外机械动作。
- 减少分包、等待和重复语音提示。

### 8.2 `U` 宏

`FFF3` 没有原生物理 `U` 编码。对于手动公式或五面求解失败后的普通解法，仍可通过翻转机构把 `U/U2/U'` 展开成五轴动作。

当前宏的基本结构为：

```text
F B R2 L2 B' F'  D...  F B L2 R2 B' F'
```

中间的 `D...` 根据 `U`、`U2` 或 `U'` 选择 `D`、`D2` 或 `D'`。相邻的同面动作会在编码前合并或抵消。

该宏保证普通六面公式仍可执行，但动作数明显增加，因此只作为手动公式兼容路径或求解 fallback，不是 Robot 状态求解的首选路径。

## 9. 其它已知命令

### 9.1 `FFF1` order

`FFF1` 写入一个 8-bit `order` 字段。具体 command enum 尚未确认。当前连接、自检、探测、打乱和复原均未发现必须使用它。

### 9.2 `FFF5` 单步机械动作

已知 payload 格式为：

```text
byte 0      = 0x21
byte 1      = direction
byte 2      = surface
byte 3..4   = turns，16-bit，大端
```

目前尚未确认：

- `direction` 的枚举。
- `surface` 的枚举。
- `turns` 的单位。

已观察的连接自检、方向探测、打乱和复原都使用 `FFF3`，没有证据表明 `FFF5` 是正常公式执行或速度优化所必需的命令。

### 9.3 `FFF4` RGB

另有写入 RGB 的格式：

```text
byte 0 = 0x03
byte 1 = r
byte 2 = g
byte 3 = b
```

颜色范围、持续时间、灯效模式以及它与 `0x03` 状态通知的关系尚未验证。

## 10. 加密

Robot 当前协议的 `isEncrypt=0`，所以 Robot 的实际 BLE payload 不需要再经过智能魔方使用的 AES 加密层。

## 11. 当前项目实现

本项目将 GAN Robot 作为独立的可选执行设备，可与智能魔方并发连接，但不接入计时状态机或成绩保存链路。

### 11.1 代码结构

- `GanRobotProtocol`：保存 V2 UUID、开启 `FFF4` notification、设备识别和按钮事件识别。
- `GanRobotCodec`：解析公式、处理 `U` 宏、合并相邻同面动作，并编码 18-byte `FFF3` payload。
- `GanRobotBleClient`：负责扫描、手动／自动连接、GATT 生命周期、descriptor/characteristic callback、`FFF3` 写入和 `FFF2` 读取。
- `GanRobotExecutor`：负责连接自检、方向探测、状态到状态编排、公式执行、`FFF2` 轮询和 solver 预热。
- `GanRobotFiveFaceSolver`：根据当前方向禁用映射到物理 `U` 轴的逻辑面，生成五面解法。
- `GanRobotController`：处理 Robot 实体按钮单击。
- `GanRobotSessionState`：在主页、智能魔方和 Robot 之间传递目标状态、当前状态和动作状态。

### 11.2 已完成项目

- 识别通常以 `GANBOT-` 开头且使用 `FFF0` service 的设备。
- 支持手动扫描、连接、断开和自动连接。
- Robot 页面打开时会同步已经由自动连接建立的真实连接状态。
- 等待 `FFF4` CCCD descriptor write 完成后再发送命令，避免 GATT command collision。
- 连接后使用单条 `FFF3` 执行 `R F D L B` 五轴自检，且不会产生额外“工作中”语音。
- 按 4-bit 动作、`0xF` 结束符、zero padding 编码固定 18-byte payload。
- 每个 `FFF3` 最多编码 35 个动作，只有超过上限才分包。
- 将方向探测的 `D`、`F` 合并为一条 `FFF3`，同时保留两次智能魔方状态判定。
- 根据探测结果建立动态 `logical -> physical` 映射，不假设逻辑 `U` 就是 Robot 缺少的物理轴。
- 使用专用五面 solver 生成不经过物理 `U` 轴的状态到状态解法。
- 五面 solver 使用约 500ms 的 anytime 搜索窗口；先取得可行解，再在剩余时间内尝试缩短公式。
- solver 表在连接自检后预热；同一进程内静态表只实际建立一次，重新连接时的重复 warm-up 基本只检查缓存。
- 五面结果会先在逻辑魔方状态上验证；超时或验证失败时才 fallback 到普通 min2phase，再由 `U` 宏保证可执行。
- `FFF2` 使用 100/200ms 自适应轮询，并处理“尚未观察到 busy 就先读到 0”的竞态。
- 记录 probe、solver、动作执行和总耗时，以及 `FFF2` 首值、最后非零值、读取耗时和 timeout 状态。
- 监听 `FFF4` 的 `0x02` 实体按钮单击事件，可触发复原、打乱或忽略。
- 支持手动公式、根据智能魔方状态复原、根据目标状态打乱和实体按钮动作。
- Robot 动作期间只同步智能魔方状态，不进入 `enterTime`、起停表、成绩保存或解法统计。

### 11.3 尚未实现或尚未确认

- 尚未支持 `5833FF01/5833FF02` read/write variant。
- 尚未完整解析 `FFF4` 的 `cubeOn`、`robotReady`、`robotStatus` 和 `robotTime`。
- 尚未确认 `0x02` 事件除单击以外是否还有其它 payload。
- 尚未使用 `FFF1/order`。
- 尚未使用 `FFF5` 单步机械动作。
- 尚未读取 `180A/2A23~2A29` 设备信息。
- 尚未实现 RGB 灯效控制。
- 动作完成仍以 `FFF2` 轮询为准，尚未确认能否可靠地改用 V2 状态通知。
- 设备识别仍以名称和基础 service 为主，尚未根据 firmware 或完整 GATT capability 自动选择 variant。

以上结论以当前 V2 真机和已有封包验证为准；未列为“已完成”的字段与命令仍应视为待验证。
